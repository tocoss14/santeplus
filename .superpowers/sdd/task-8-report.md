**Concerns:**
- Population stddev (/N) used; switching to sample (/N-1) would lower threshold slightly (2.04 vs 2.23 for 50000 outlier with 5 normals) but still >2 for this seed. If network has <2 eligible providers, detection returns [] (needs ≥2 to compute stddev); small networks (<6 providers) have volatile Z.
- Z-score computed on `totalApproved ?? totalRequested`; if claims have mixed currency or partial approvals, avg may be biased. Consider using `totalApproved` only when present, else skip claim, or normalize per `totalRequested`.
- Cumul groups by `Claim.items[].code` and `claim.careDate` day; if fraud spans `DeliveryLine` without linked Claim or uses different date fields (createdAt vs careDate), grouping may miss. Extending to `Delivery` lines would improve coverage; current matches spec "same contract, same medication code, different beneficiaries, same day".
- Admin anomalies fetch uses `audit.view` permission — ensure frontend role `audit.view` is granted to `SUPER_ADMIN`/`INSURANCE_MANAGER`; otherwise dashboard section shows "Alertes indisponibles" silently.
- No DB migration (reuses AuditLog/Notification); prod needs no schema change but `CronService` now boots two jobs at 02:00 and 02:30 — ensure single instance deployment to avoid double alerts.
- `AdminDashboard` fetch of `/admin/anomalies` assumes `items` shape `{items:[]}`; defensive `res.items ?? res` handles both enveloped and raw array during rollout.
